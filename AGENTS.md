# Workspace Rules for HermitUI

Welcome to the `AGENTS.md` file! This file dictates the strict architectural constraints and workflow rules for HermitUI.

## 🏗️ Architecture & Frameworks
- **Single File Output Constraint:** The generated application must remain entirely within a single `.html` file. During development, the source code in `src/` is split into `index.html`, `style.css`, and `script.js` for maintainability. The `build.py` script assembles them into the single-file output.
- **No Build Tools:** Do NOT add `package.json`, `npm`, Webpack, Vite, or any other Node.js build tools. 
- **Vanilla Only:** Do NOT use React, Vue, Angular, or any frontend frameworks. Use modern Vanilla JavaScript (ES6+) only.
- **No CSS Frameworks:** Do NOT use TailwindCSS, Bootstrap, or any CSS preprocessors. Use Vanilla CSS.

## 🛠️ Build Flow & Outputs
The source code is modularized within the `src/` directory (`index.html`, `style.css`, `script.js`). `src/index.html` references external libraries via CDN for convenient local development. Everything else is generated by `build.py` — **never edit generated files directly**, they are overwritten on the next build.

Run the build with:
```bash
python build.py   # or python3 build.py — regenerates all outputs from src/
```

`build.py` downloads the pinned library versions (Marked.js, DOMPurify, Highlight.js, KaTeX, Mermaid, Inter font) into `libs/`, inlines `src/favicon.svg`, then does regex-based substitution of the CDN `<script>`/`<link>` tags. If you change a CDN tag in the source, the matching regex in `build.py` must still match it. Mermaid (~3.5 MB) is special-cased: instead of being inlined plainly it is gzipped + base64-encoded and injected as `window.__MERMAID_INLINE__` into the single-file outputs (its version pin lives only in the `src/index.html` CDN tag), and `src/script.js` inflates it in-browser via `DecompressionStream` the first time a diagram is rendered. Generated outputs:
- `dist/hermit-ui-standalone.html` — fully standalone: all JS/CSS/fonts inlined and base64-encoded. The primary deliverable.
- `index.html` (root) — copy of the standalone build, served as the GitHub Pages landing page (the final build step copies it out of `dist/`).
- `dist/hermit-ui-cdn.html` — same as the source (CDN links).
- `dist/hermit-ui-local.html` — links rewritten to point at `../libs/`.
- `dist/hermit-ui-wllama.html` — standalone build **plus** the in-browser (wllama) inference backend. All wllama code in `src/` lives between `@wllama:start`/`@wllama:end` marker comments (`<!-- -->` in HTML, `/* */` in CSS, `//` in JS); `build.py` strips those blocks for every other output, so the main app stays lean. The wllama engine itself (JS + WASM, pinned via `WLLAMA_CDN_BASE` in `src/script.js`) is downloaded by `build.py`, gzipped + base64-encoded, and injected as `window.__WLLAMA_INLINE__` in place of the `<!-- @wllama:inline-engine -->` placeholder in `src/index.html`, so this output runs fully offline; the unbuilt dev source falls back to a jsDelivr `import()` at model-load time.

There is no linter or package manager. To verify a change, open `index.html` (or `dist/hermit-ui-standalone.html`) in a browser after building. `tests/` holds a small suite covering the pure logic only — Export/Import round-trips plus think-tag parsing, endpoint/URL normalization, cloud-provider detection, file-type gating, the wllama prompt builders and chat error hints; run `node tests/run.mjs` (no install needed) and, after a build, `benchmark/.venv/bin/python tests/e2e_export_import.py`. The unit tests slice the real functions out of `src/script.js` via `tests/extract.mjs`, so renaming one fails the suite loudly — update the extractor with the rename. Anything touching the DOM can't be unit-tested this way; cover it in the end-to-end test. See `tests/README.md`. `dist/hermit-ui-standalone.html`, `dist/hermit-ui-cdn.html`, and `dist/hermit-ui-wllama.html` are committed (browsable on GitHub); `dist/hermit-ui-local.html` and `libs/` are gitignored.

## 🧩 Code Structure within `src/`
The code is split into `index.html`, `style.css` (which contains both the light theme and dark mode overrides), and `script.js`. Theming is driven by CSS variables and a `data-theme` attribute on `:root`. Key JS areas:
- **Personas** (`PERSONAS` const, `switchPersona`, `activePersona`/`SYSTEM_PROMPT`): preset system prompts selectable via a dropdown.
- **Streaming** (`fetchAndStreamChat`): SSE-style fetch loop that parses streamed chunks and fires `onChunk`/`onDone`/`onError` callbacks; `createThrottle` rate-limits UI re-renders during streaming.
- **Thinking-tag parsing** (`parseThinkSegments`): extracts and renders `<think>`/`<thought>`/`<reasoning>` segments separately from the answer. Preserve this when touching rendering.
- **Message rendering** (`updateMessageUI`, `appendMessage`, `injectCopyButtons`): Markdown via Marked.js, syntax highlight via Highlight.js, per-code-block copy buttons; supports edit/regenerate.
- **Math & diagrams** (marked math extensions + `renderMathTex`, `loadMermaid`/`renderMermaidBlocks`, shared `gunzipToBytes`): LaTeX math renders through KaTeX in MathML-only mode (no fonts/CSS) inside the normal `marked.parse` → `DOMPurify.sanitize` pipeline; ```` ```mermaid ```` fences are replaced with sanitized SVG only on final message renders (`securityLevel: "strict"`, HTML labels off — output must stay pure SVG so DOMPurify doesn't gut it). Invalid diagrams must keep degrading to plain code blocks.
- **Settings & connection** (settings modal handlers, `testConnectionBtn`): API URL, model name, system prompt, API key; live performance stats via `updateGlobalStats`.
- **Chat error display** (`chatErrorHint`, `chatErrorHtml`): a failed reply shows the raw error plus one line of advice picked by failure class — dead/out-of-memory in-browser engine, 401/403 → API key, 404 → URL/model, 429, 5xx, context overflow, network error (local vs cloud wording, blocked mixed content first). `chatErrorHint` is pure and unit-tested; add new failure classes there rather than hard-coding text at a call site. An empty hint means the error already says enough. **Test Connection** reuses it (throwing the same `Server Error NNN: detail` shape) in a red `showToast(msg, { error: true })` that stays up 8 s; a non-JSON answer (Base URL pointing at a web UI) is its own class. The wllama build also shows a Firefox-only notice (UA-sniffed on purpose — it's a bug, not a missing capability) that WebGPU decode is <1 tok/s there because Firefox polls GPU completions on a 100 ms timer ([bug 1870699](https://bugzilla.mozilla.org/show_bug.cgi?id=1870699)); remove it once that fix ships.
- **Context attachments** (`processFiles`, `renderChips`, `isTextFile`): drag-drop / upload of text files injected into the prompt.
- **Export** (`exportBtn`): downloads the conversation as Markdown.
- **Reasoning effort** (`thinkingControl`/`setThinkingLevel`, `parseReasoningTemplateSupport`, `buildReasoningParams`, `apiRoot`, `probeReasoningSupport`, `updateThinkingControl`): an Off/Low/Med/High segmented control in the composer toolbar (see **Composer layout** below). It ships in **all** builds (only the wllama call site sits inside marker blocks). Levels map per backend: wllama sends `chat_template_kwargs {enable_thinking, reasoning_effort}` (wllama 3.6.1+ forwards these per call), remote sends the OpenAI-standard `reasoning_effort`, with `enable_thinking:false` as the only way to express "off". "High" resolves to whatever the template calls its maximum — Qwen3.5/3.8 use `xhigh`, everyone else `high`. **A level the template does not list is dropped, never sent:** Qwen3.5/3.8 validate `reasoning_effort` against exactly `('xhigh','medium','low')` and `raise_exception` on anything else, and the OpenAI-standard `"high"` is *not* in that set — wllama surfaces the raise as the opaque `Invalid magic number`. `parseReasoningTemplateSupport` therefore reads the accepted set out of the template's own validation clause rather than guessing; `looksLikeReasoningRejection` also matches the prose a template raise produces, since it never names the JSON key.
  Capability detection, because a dead knob is worse than no knob: for a local GGUF the embedded `tokenizer.chat_template` is scanned for the variables (a template that never references them provably ignores them); for a remote endpoint the settings modal has a **Check Reasoning Support** button that reads llama.cpp's `/props` → `chat_template_caps.supports_reasoning_effort`, falling back to Ollama's `/api/show` template. Endpoints exposing neither stay "unknown" and the control is shown optimistically. **Do not "improve" this by probing with a throwaway completion** — llama.cpp answers `200` for parameters it silently ignores (verified with a deliberately bogus param name), so a non-error proves nothing. Strict servers that *do* 400 are handled instead by stripping `REASONING_PARAM_KEYS` and retrying once, after which the control hides itself.
- **Composer layout** (`#chatForm` → `.input-shell` → `.composer-toolbar`): the composer is one card — the textarea on top, and a control row along its bottom edge holding the persona `<select>`, the reasoning-effort segmented control and `.composer-actions` (attach / send / stop). `#chatForm` is a bare layout wrapper; **all** card styling (background, radius, border, `:focus-within`, the `is-generating` glow) belongs to `.input-shell` — `is-generating` is still toggled on the form by JS, hence the `#chatForm.is-generating .input-shell` selector. The toolbar is `flex-wrap: wrap` with `margin-left: auto` on the actions: that, and not a media query, is what keeps a 420px viewport from overflowing, so don't replace it with fixed widths. The reasoning control is a `role="radiogroup"` of `<button>`s with roving tabindex; **every segment needs `type="button"`** — they sit inside `#chatForm`, so a default-type button submits the message on click.

- **In-browser inference** (`@wllama:start`/`@wllama:end` blocks: `backendMode`, `CHAT_TEMPLATES`, `buildWllamaPrompt`, shared `loadWllamaModel`, wllama branch in `fetchAndStreamChat`): local GGUF chat via wllama, only present in `dist/hermit-ui-wllama.html`. Models load from a local file picker or by URL (`normalizeGgufUrl` accepts direct `.gguf` links, HF `/blob/` URLs rewritten to `/resolve/`, and the `hf:user/repo/file.gguf` shorthand; `downloadGgufToBlob` streams into an **in-memory Blob**). Do NOT switch to wllama's `loadModelFromUrl` — it persists models to OPFS even with `useCache: false`, violating the ephemerality rule. New wllama-only code must stay inside marker blocks, and stripping must leave the remaining code valid.
- **wllama and reasoning output:** the model load passes `reasoning_format: "none"`. llama.cpp's default (`auto`) parses a `<think>` trace out of the content into a *separate* reasoning field, which the wllama `onData` handler never reads — a model that thinks at length then streams zero content and the answer renders empty (observed: Qwen3.8-27B spent 480 s on one puzzle and produced 0 counted tokens). Inline is also the form `parseThinkSegments` already expects, so the trace renders as a normal collapsible think block. Do not remove this without re-testing a *hard* prompt — short answers don't trigger a reasoning trace and will look fine either way.
- **wllama `loadModel` does not throw when the context can't be created:** if llama.cpp loads the weights but fails to allocate the context (typically the KV cache for a large `n_ctx` — 32768 needs ~3.5 GB for Qwen3-0.6B on CPU — not fitting the WASM heap), wllama 3.6.1 resolves `loadModel` anyway with `success: false` and empty metadata. The app used to report "Ready", fall back to the `zephyr` format, hide the reasoning control, and then every call died with `Invalid magic number`. The load loop now checks `getLoadedContextInfo().success === false` and throws a `ContextAllocError` into the existing halve-`n_ctx`-and-retry path; if it still fails at the 4096 floor the status line says to pick a smaller model (or enable WebGPU, when available and off). The default Context Window is **16384** (was 32768, which failed on CPU in every browser and only worked via the retry) — it fits Qwen3-0.6B on the first try. Keep the check; test CPU mode at the *default* context, not just the 4096 the benchmark uses. Note that Context Window **0** does not mean "the model's trained context" in wllama 3.6.1: `loadModel` falls back to its own `n_ctx` default of 1024.
- **wllama tail-token bug (fixed upstream, no patch needed):** wllama 3.5.1 stranded the final tokens of every completion in the worker's result queue (`has_more` reflected *task*-queue emptiness, so it could go false while results were still queued) — answers were cut off mid-word and the missing tail bled into the start of the next answer. HermitUI carried a `patchWllamaGetResponse` override for this; it is **gone** as of the 3.6.1 bump. Upstream fixed the root cause in the wasm layer instead (ngxson/wllama#269, released in 3.6.0): `wllama_context::action_get_result` now ORs in `rd->has_next()`, so `has_more` tracks the response reader rather than the task queue, and the JS loop's `break` on `!has_more` is finally correct. Our issue #263 was closed as completed; our PR #264 was closed unmerged as superseded. **Do not reinstate the override** — 3.6.x scopes `get_result` to a `req_id` (`getResponse(options, isStream, reqId)`) and cancels the request in a `finally`, so an override written against the 3.5.1 signature breaks every completion. Note 3.6.x aborts with its own `WllamaAbortError` (`name` "AbortError", `message` "Operation aborted"), which is why the Stop path in `fetchAndStreamChat` matches on `err.name` as well as `err.message`.

## 🎨 Styling & UI/UX
- **Aesthetics:** Maintain the modern "glassmorphism" feel. Use smooth animations, CSS variables for theming, and the `Inter` font.
- **Responsiveness:** Ensure all CSS changes remain mobile-responsive by leveraging fluid design principles (like flexbox and max-width). Avoid explicit media queries to keep the CSS simple unless absolutely necessary.

## 🔒 Security & Data
- **Ephemeral State:** Do absolutely NOT implement `localStorage`, `IndexedDB`, or cookies for ANY reason (including settings, preferences, or conversation history). Privacy and strict ephemerality are core features.
- **Sanitization:** Any text returned by the AI that is rendered as HTML or Markdown MUST be sanitized using `DOMPurify.sanitize()` to prevent XSS attacks.

## 🤖 AI & API Integration
- **API Compatibility:** All network requests must strictly adhere to the OpenAI chat completions API schema. 
- **Thinking Tags:** Ensure any UI changes preserve the ability to parse and elegantly render `<think>`, `<thought>`, and `<reasoning>` tags.

## 🏎️ Model Benchmark Harness (`benchmark/`)
A self-contained Playwright harness that races GGUF ladders (Qwen3 0.6B → 1.7B → 4B → 8B and Gemma-4 E2B → E4B → 12B, all Q4_K_M, plus a standalone gpt-oss-20b MXFP4 rung) through the **unmodified** `dist/hermit-ui-wllama.html` — via the `#gguf=` hash param and the app's own buttons — measures TTFT / tok/s, has every model answer the 10 demo questions in `benchmark/questions.json`, and writes `results/<timestamp>-<backend>/review.md` + `run.json` with a recommendation. See `benchmark/README.md` for setup; `models/`, `results/`, `.venv/` are gitignored (models are cached on disk by the harness — the app itself stays fully ephemeral). The rungs above ~4 GB (Qwen3-8B, Gemma-4-E4B, Gemma-4-12B) need WASM Memory64 (current Chrome/Edge); without it they fail to load and that is the device's recorded ceiling. A too-slow/failed rung only skips the rest of its own family. The `/no_think` suffix is only sent to models flagged `"nothink"` in the ladder (Qwen3).

Operational rules learned the hard way — keep future runs working:
- **Line-buffer stdout in every harness script** (`sys.stdout.reconfigure(line_buffering=True)` at the top, already in place). Python block-buffers stdout when redirected to a log file, so without this a 20-minute run looks completely silent to `tail -f`/monitors until exit. Any new print-based progress must flush per line.
- **Warm up before recording any timing.** Send one or more throwaway requests after a model loads and discard them; only measure once the model is warm. The first request after a load pays one-off costs (graph/kernel warm-up, cold-KV prompt eval, allocator growth) that never recur, so it badly overstates latency — Qwen3.8-27B measured 24.4 s TTFT on the first question after load versus 17 s on a later run of the same shape. Every reference figure quoted in this file is a warm number; say so whenever quoting a single run.
- **Emit a progress line *before* long silent phases** (model load, each question), not only after — a 4B question can take minutes.
- **Long runs must be launched detached** (`nohup … > run.log 2>&1 &`) — a full ladder run exceeds typical agent tool timeouts; watch the log instead of blocking.
- **GPU mode (WSL2):** headless Chromium inside WSL only gets SwiftShader WebGPU. `run_benchmark.py --gpu` launches Windows Edge (`--headless=new --enable-unsafe-webgpu`, CDP port 9223) via interop and connects with `connect_over_cdp`; mirrored networking makes 127.0.0.1 work in both directions. Edge must be terminated via the CDP `Browser.close` command — Playwright's `close()` only disconnects.
- Reference results on the dev machine (16 threads / RTX 5070 Ti, July 2026): CPU → 0.6B ≈ 15 t/s, 1.7B ≈ 10 t/s, 4B ≈ 3 t/s (recommendation 1.7B); GPU → 0.6B ≈ 68 t/s, 1.7B ≈ 63 t/s, 4B ≈ 47 t/s (recommendation 4B).
- Gemma-4 reference (same machine, July 2026): prompt processing in wllama is much slower than Qwen3's, so TTFT dominates (E2B: ~40 s TTFT on CPU, ~10 s on GPU) and the app-reported tok/s craters even though decode is fast (E2B GPU ≈ 39 t/s decode but ≈ 6 t/s app-reported; E4B GPU ≈ 30 t/s decode at ~11 s avg TTFT → app-reported hovers around the 5 t/s threshold: an early-stopped standard run scored it too_slow at 4.6, a full 10-question run averaged 6.3 with all answers correct). CPU → no Gemma rung usable; GPU → recommendation E2B, with E4B borderline-usable for those who tolerate the initial wait. 12B (7.1 GB Q4_K_M) loads via Memory64 — the current in-browser size ceiling — and decodes at ≈ 33 t/s GPU, marginally *faster* than E4B (the E-series per-layer embeddings cost wllama more than dense size does), but ~14 s avg TTFT puts app-reported at ≈ 4.2 t/s; all answers correct. Both rungs load fine (wllama 3.5.1 supports the arch; E4B via Memory64), answers are clean — Gemma is simply a worse fit for wllama than Qwen3 until prompt eval gets faster.
- gpt-oss-20b reference (MXFP4, `ggml-org/gpt-oss-20b-GGUF`, same machine, 2026-07-21, 4 clean GPU runs): **12.1 GB loads reliably** in ≈ 78–84 s and decodes at ≈ 43 t/s — *faster* than dense Gemma-4-12B, since only ~3.6B params are active per token. App-reported ≈ 15 t/s at ≈ 3.4 s avg TTFT; the gap is larger than for other models because gpt-oss emits a hidden reasoning trace whose time lands in the app's denominator while its tokens don't (a correct 31-char logic answer read 2.9 t/s app vs 40.5 t/s decode). Answers were correct throughout. TTFT is uneven in a way the average hides — 1.4–3.9 s on the knowledge/reasoning/code/German questions but several seconds longer on the two writing prompts — while decode stays flat at 41–43 t/s, so prompt length moves TTFT far more than it moves throughput. Worth re-measuring when `WLLAMA_CDN_BASE` is next bumped.
- **The GPU must be idle for a `--gpu` run — the harness now enforces this.** `check_gpu_idle()` queries `nvidia-smi` before launching Edge and aborts if more than `VRAM_IDLE_LIMIT_MB` (1500) is already resident, naming the processes holding VRAM; `--allow-busy-gpu` overrides and flags the run instead. VRAM at start/end goes into `run.json` (`vram_before`/`vram_after`/`gpu_contended`) and the `review.md` header, so an old result can be audited after the fact. If `nvidia-smi` is missing the run proceeds but is marked unvalidated. Why it matters: the first gpt-oss-20b pass was measured with a game holding ~11 GB of the 16 GB card and recorded 1.9 t/s decode / 39 s TTFT — a 23× understatement versus the same build on a free GPU (43 t/s / 3.4 s), and it wrongly looked like an MXFP4 kernel problem. Model *loading* is unaffected (Memory64 puts weights in the WASM heap), so a contended run completes normally and only the tok/s is wrong.

## 🔄 Git & Versioning Workflow
- **Check Origin:** ALWAYS check origin for change or new Stuff before start of edit or task
- **Pre-Commit Review:** ALWAYS conduct a careful review of your changes before executing a `git commit` to ensure everything is correct, strictly adheres to the rules, and does not introduce any bugs or inconsistencies.
- **Build Before Commit:** ALWAYS run `python3 build.py` to regenerate the compiled files before executing a `git commit`.
- **Ask Before Committing:** Do NOT `git commit` on your own. When a task is done, report it and leave the changes uncommitted; commit only when the user explicitly asks for it.
- **Ask Before Pushing:** Do NOT push commits to GitHub (or any remote repository) unless the user explicitly asks for it.
- **Agent Rules:** This root `AGENTS.md` is the single source of truth for agent rules and is committed to the repo (read directly by Antigravity, and by Claude Code via the gitignored `CLAUDE.md` symlink). Keep the `CLAUDE.md` symlink local — do not commit it.
- **Version Bumping:** Whenever a new version is tagged in git, automatically update the version number within the `src/index.html` file to match.

## 📝 Safe Refactoring Workflow
- **No Plan Required:** An Implementation Plan (`implementation_plan.md`) and plan approval are no longer required before implementing a change. Write one only when the user asks for it.
